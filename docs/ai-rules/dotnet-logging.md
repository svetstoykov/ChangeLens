# Logging

Read before adding or changing any backend diagnostics, log statement, or logging configuration.

Logging is an important part of ChangeLens correctness, supportability, and auditability. Preserve these practices whenever backend behavior is added or changed:

- Inject `ILogger<T>` into engine, infrastructure, and core services. Do not use `Console`, static loggers, or provider-specific logger types for application diagnostics.
- Configure logging providers only at the Engine composition boundary. Engine, Infrastructure, and Core implementations depend only on the Microsoft logging abstraction (`Microsoft.Extensions.Logging.Abstractions`), never a concrete provider. `ChangeLens.Core` stays free of other ChangeLens project references and of heavyweight or provider-specific packages, but the logging abstraction is an accepted, deliberate exception to Core's general "minimal dependencies" preference: Core does not have to be dependency-free, only disciplined about which dependencies it takes. Add `ILogger<T>` to a Core service whenever that service contains non-trivial branching, multi-step orchestration, or its own failure modes worth tracing — do not add it to simple pass-through types, value objects, or trivial mappers just for uniformity.
- Keep standard output reserved exclusively for versioned engine protocol messages. Console diagnostics must go to standard error, and rolling local-file logging must remain available.
- Use structured message templates with stable, descriptive property names. Do not use string interpolation to build log messages.
- At `Information`, record meaningful lifecycle and operation outcomes with available correlation identifiers, method or operation names, stable error codes, and elapsed time. Use `Debug` for detailed diagnostic payloads and step-by-step flow through complex or branching logic (e.g., which path a comparison or discovery algorithm took and why). Use `Warning` or higher for degraded or unexpected conditions.
- Never log secrets, credentials, unrestricted source content, or other sensitive data. Local filesystem paths (selected repository paths, canonical paths, canonical path keys) are treated as sensitive: never log a raw, unprocessed path at `Information` or above, including inside a message that is otherwise about a normal outcome. Raw paths may appear only at `Debug`, only when their schema has been reviewed for sensitive fields, and must be removed or redacted when that assumption changes. Prefer a non-path identifier instead — a repository's display name, a stable ID, a Git ref name, or just the outcome with no identifier — before reaching for `Debug`-only path logging. The same caution applies to raw protocol payloads and file contents.
- `PathSanitizer.ToRepositoryRelativePath` is the only helper that makes an arbitrary path safe at `Information`. It anchors the path to a known `RepositoryDescriptor` root and emits the repository display name plus the relative path, or a fixed placeholder when the path falls outside that root. `PathSanitizer.RedactHomeDirectory` replaces a home-directory prefix with `~` and returns every other path verbatim, so it makes a path shorter rather than safe: use it only for paths already known not to be user content, such as the configured Git executable, and never to launder a caller-supplied repository path into an `Information` message. Never bypass the helper with ad hoc string manipulation (`Replace`, `Substring`, manual prefix stripping) to produce a "safe-looking" path for `Information` logging.
- An exception carries its own path into the log entry whatever the message template says: `UnauthorizedAccessException` and `DirectoryNotFoundException` both quote the path they failed on, and a `FileNotFoundException` constructed with a file name renders it too. Sanitizing a `{Path}` argument in the same call changes nothing and implies a guarantee that is not there. Log a filesystem exception at `Debug`, let the exception carry the path, and keep the path out of the message template.
- Log expected failures once, at the layer with the most context about *why* the failure occurred (often where the `Result` is produced, not just where it is forwarded), without adding side effects to Result forwarding. Do not re-log the same expected failure at every layer it passes through. Log unexpected exceptions once at the exception boundary and include the exception object.
- For infrastructure that shells out, hits the filesystem, or talks to a datastore (git CLI invocation, SQLite access, path resolution), log the operation attempted, its outcome, and elapsed time at `Information`, and log full command/argument or query detail at `Debug`. These are the areas most likely to fail in ways only visible from logs.
- Add or update tests for logging behavior that is part of a process or protocol contract, especially the rule that diagnostics cannot pollute standard output. Assert path sensitivity against the operator-facing projection of the captured log, `EngineLogEntries.InformationAndAbove`, so a `Debug` entry stays free to carry the detail that reproduces a failure. Assert protocol payloads, freshness tokens, and caller-supplied query text against the whole log, at every level.
- Pass a structured logging argument as the lazily-evaluated `IEnumerable<T>` the logging pipeline already expects (e.g. `errors.Select(error => error.Code)`). Do not append `.ToArray()` or another eager materialization; it only adds an allocation with no benefit, since the logging provider enumerates the sequence itself.
